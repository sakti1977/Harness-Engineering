# Build a harness universe readers can use

**The strongest next step is to connect the vault's concepts to trustworthy sources, working examples, and evidence that a harness change helps a real project.** The local vault has a useful conceptual skeleton, but its original 44 Markdown files contain only about 6,395 words and no external source URLs; the existing source index maps earlier conversation material rather than an independently checkable bibliography. The public repository should become the practical companion: diagnose a project's weaknesses, install a small set of appropriate controls, and measure the result. This research reviewed a curated set of 13 repositories with at least 1,000 visible stars, eight first-party engineering articles, and additional official material on evaluation, security, infrastructure and reliability. It does not exhaust every credible repository or blog, and upstream benchmark claims were not reproduced. The recommended roadmap starts with correctness and a runnable starter, then broadens into source-backed lessons, adapters and reproducible experiments. Thousands of stars and clones are an adoption ambition; useful first experiences, credible evidence and sustained maintenance are the work that can support it.

## Establish trustworthy foundations before expanding the catalogue

The original vault's strengths are its consistent vocabulary, linked five-layer model, permission and scope contracts, evidence-led completion, journals and checkpoints. Preserve these. Label Reach, Power, Ground, Verdict and Carry as **this vault's organizing synthesis**, because their external origin has not been established. Preserve the original [[Source Coverage Index]] as the record of the earlier material. Add a separate source register instead of suggesting that newly found publications authored the existing text. Two substantive notes, [[Copilot Project Instructions]] and [[Case Studies - MOC]], also need prominent entry links. The baseline and detailed coverage assessment are recorded in [the local vault audit](../research_notes/Harness%20knowledge%20base%20expansion/vault_gaps.md).

Every maintained concept should answer a real question: what fails, which mechanism helps, when it is inappropriate, how to reproduce the failure, and what observation shows the control worked. Every factual source claim should carry its publisher, date, URL, access date and relevant version. Distinguish **source finding**, **local recommendation**, **hypothesis**, and **verified local result**. For implementation evidence, record the commit and inspected file; for vendor experiments, retain model, task and environment limits. The exact numerical clinic scenarios currently lack incident provenance. Mark them instructional scenarios until original evidence is recovered, and remove unsupported precision where it adds false authority.

The engineering literature supports improving the system surrounding the model, but it does not prescribe one timeless architecture. OpenAI describes repository documentation checks, architectural boundaries and observability in its own heavily invested-in development environment. Anthropic's earlier long-running application experiment uses initialization and persistent progress artifacts; its later work examines which scaffolding remains worthwhile as models change. The practical implication is to teach both how to add a control and how to test whether it should remain. ([OpenAI harness engineering](https://openai.com/index/harness-engineering/); [Anthropic long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents); [Anthropic harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps))

Use the thousand-star filter for discovery, followed by owner provenance, inspectable implementation, maintenance status and relevance. The research inventory includes Codex, Claude Code, OpenHands, AutoGen, Aider, LangGraph, smolagents, PydanticAI, SWE-agent, mini-swe-agent, SWE-bench, Claude Agent SDK demos and OpenHands Software Agent SDK. Their rounded observed counts and review depths are in [the repository register](../research_notes/Harness%20knowledge%20base%20expansion/repositories.md). Avoid treating these projects as interchangeable frameworks: Claude Code's repository is product-facing rather than a full runtime release; Anthropic labels the SDK examples local demos; SWE-agent directs new development toward mini-swe-agent; AutoGen identifies itself as maintenance mode. These distinctions belong beside recommendations, not in a hidden footnote. ([Claude Code](https://github.com/anthropics/claude-code); [SDK demos](https://github.com/anthropics/claude-agent-sdk-demos); [SWE-agent](https://github.com/SWE-agent/SWE-agent); [AutoGen](https://github.com/microsoft/autogen))

## Teach the missing mechanisms through failures readers can reproduce

**The highest-value expansion is an evaluation spine connecting every layer.** Separate deterministic harness-control tests from stochastic task evaluations. A permission check can have a deterministic expected result, while a coding task needs repeated trials, an outcome grader and a record of its environment. Explain task, trial, trace, grader and final state; distinguish capability suites from regression suites, and success at least once from consistency across attempts. Teach readers to calibrate model graders against human judgments and to accept valid alternative solutions rather than requiring an exact tool-call sequence. ([Anthropic agent evaluations](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents))

Create a small benchmark pack from the vault's existing failure stories: a false-green booking outcome, a forbidden write, an interrupted external effect, lost checkpoint context, stale evaluation evidence and conflicting edits. Each fixture needs an initial state, permitted actions, expected final state, negative control, proof command and reset procedure. Protect the grader from the agent under test where the execution setup supports that boundary. Store raw evidence alongside the score. A simulated fixture proves the modeled behavior; label real process, network and sandbox tests separately so users know which boundaries were exercised. SWE-bench demonstrates why provenance matters: its evaluation results can be cached by run and instance identifiers even when a patch changes. ([SWE-bench](https://github.com/SWE-bench/SWE-bench))

Broaden Power beyond file paths. Add untrusted documents and tool outputs, prompt-injection trust boundaries, connector identity, token audience, network egress and private-network requests. Explain that schema validity, authorization and factual correctness are three separate checks. MCP's security guidance addresses confused-deputy problems, token passthrough and SSRF; it cannot stand in for a complete prompt-injection defense review. Add a focused primary-source security review before publishing a comprehensive mitigation recipe. Codex's implementation documents platform-dependent enforcement, while smolagents explicitly says its local Python executor is not a security sandbox. ([MCP security guidance](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices); [Codex core](https://github.com/openai/codex/blob/main/codex-rs/core/README.md); [smolagents](https://github.com/huggingface/smolagents))

Expand Carry and Runtime with retry classification, bounded attempts, idempotency keys, crash reconciliation, cancellation races and memory retention. A lost response does not prove a write failed; a cancellation acknowledgment does not undo completed effects. A lab should crash after an effect but before its receipt, then reconcile without blindly repeating the write. Distinguish conversation state, resumable checkpoints and durable project knowledge, and test cross-thread isolation and removal of stale memory. ([AWS idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/); [AWS retry timing](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/); [Codex app-server](https://github.com/openai/codex/blob/main/codex-rs/app-server/README.md); [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence))

Make Reach and Tools empirical. Compare preloaded context with on-demand discovery and a hybrid approach; compare plain search with repository maps; compare shell actions with structured tools. Measure missing facts, wrong-tool choices, invalid arguments, output volume, latency and successful outcomes on the same tasks. Aider supplies a concrete repository-map and lint/test-feedback example; mini-swe-agent supplies a readable minimal agent/environment/model boundary; PydanticAI supplies typed validation examples. These are comparison subjects, not universal winners. ([Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents); [Tool design](https://www.anthropic.com/engineering/writing-tools-for-agents); [Aider](https://github.com/Aider-AI/aider); [mini-swe-agent](https://github.com/SWE-agent/mini-swe-agent); [PydanticAI](https://github.com/pydantic/pydantic-ai))

Finally, connect observability and coordination to measurable overhead. Record run, parent, child and tool identifiers; termination reason; retries; token and monetary usage; latency; denial and timeout events. Redact sensitive payloads by default. Pin OpenTelemetry names because its GenAI agent conventions are marked Development. Teach delegation only where work can be bounded and integrated; compare it against one agent under the same budget, and test ownership conflicts, child failure and cancellation. Infrastructure resources also belong in experiment manifests because resource configuration can affect measured outcomes. ([OpenTelemetry agent spans](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md); [Anthropic multi-agent research](https://www.anthropic.com/engineering/multi-agent-research-system); [Infrastructure noise](https://www.anthropic.com/engineering/infrastructure-noise))

## Give the vault and repository distinct, connected jobs

The vault should explain, connect and teach; the repository should help users change their own projects with confidence. Keep the existing numbered vault structure and introduce new notes where they belong instead of replacing it with a second taxonomy. Start Here should offer three routes: a beginner understanding the layers, a practitioner diagnosing an existing project, and a maintainer evaluating a runtime change. Each milestone should end with a working artifact or a specific observation. Add sources and labs only when their content is ready; empty placeholder notes make apparent coverage grow without adding understanding.

Use a consistent concept-note contract: problem, mechanism, worked example, failure injection, verification, limitations, sources and related concepts. Use source cards with author, organization, publication and access dates, document kind, commit or version, scope, supported claims and review triggers. Use case cards with observed-versus-synthetic status, reproduction, impact, causal uncertainty and control results. Use experiment cards with baseline, hypothesis, one changed mechanism, optimization and holdout sets, run manifest, results and acceptance decision. These four templates provide a shared language between learning and implementation.

Position the public repository as **a practical harness improvement kit for existing projects**. Its main path should be: inspect a project, identify its weakest control, install the smallest relevant template or adapter, reproduce a failure, and verify the improvement. “Fine-tuning the harness” here means changing instructions, context, tools, permissions, state and evaluation around a model; it does not require training model weights. Keep the core tool-neutral. Vendor adapters should map explicit capabilities and limitations, including instruction-file locations, tool interception, approval behavior and unsupported controls. An instruction file is guidance; it does not create an operating-system sandbox.

A proposed repository layout is `docs/` for explanations and migration guides, `templates/` for reusable contracts, `schemas/` for machine-readable formats, `scripts/` for portable validation and diagnostics, `tests/` for deterministic controls, `examples/` for complete reference projects, `evals/` for task fixtures and graders, `adapters/` for vendor-specific integration, and `.github/` for CI and contribution workflows. Treat this as a target structure, not a request to create empty directories. Initially favor a small portable checker and standard-library test runner over building another orchestration framework. Add package distribution only when installation pain justifies maintaining it.

Keep one canonical Markdown source when publishing a repository handbook or web view; generate alternate navigation and check both forms in CI.

The first starter should run without a paid model key: validate a filled task contract and feature ledger, run a deliberately broken example, show rejection, apply the fix and show passing evidence. A second optional path can connect a model, with explicit cost and environment configuration. The diagnostics command should be read-only by default, produce human-readable and JSON output, explain each finding and link to its remedy. Any later installer needs a preview, conflict detection and reversible changes. A verification runner must execute only explicitly configured, trusted commands and show what it will run; it must not discover and execute arbitrary commands from an untrusted project. Never present a single maturity score as proof of safety; report the underlying checks and which boundaries remain untested.

## Ship releases with acceptance gates and realistic effort

The estimates below are planning judgments for one experienced maintainer, excluding substantial original research or external contribution delays. **Release gates matter more than calendar dates.** Do not begin a broad adapter catalogue while the starter's correctness remains unsettled.

### The public repository needs a precise first repair

The complete nine-file repository was inspected at commit `a800a594297451eab10e6ff0c9cde94a3e31aca0`. Its checker verifies file existence and required JSON keys, rejects the exact feature state `passing`, and prints `HARNESS READY` for other accepted inputs. It does not restrict state values or validate field types, run readiness probes, verify evidence, or enforce changed-file scope; malformed JSON is not caught. Its success message therefore claims more than the implementation establishes. These are static audit findings, not executed test results. ([Pinned checker](https://github.com/sakti1977/Harness-Engineering/blob/a800a594297451eab10e6ff0c9cde94a3e31aca0/scripts/harness_check.py))

The feature example refers to `src/booking.py` and `tests/test_booking.py`, which are absent. No test suite, CI workflow, license file or executable booking application exists in the inspected tree. The authority document states policies, but no runtime permission interceptor is present. Repair the language to distinguish **guidance, artifact validation, executed checks and enforced boundaries**. A completed feature should eventually be accepted when its valid status is backed by required evidence; permanently banning one spelling of completion does not establish trustworthy completion. ([Pinned feature example](https://github.com/sakti1977/Harness-Engineering/blob/a800a594297451eab10e6ff0c9cde94a3e31aca0/.harness/feature.json); [pinned tree](https://api.github.com/repos/sakti1977/Harness-Engineering/git/trees/a800a594297451eab10e6ff0c9cde94a3e31aca0?recursive=1); [authority policy](https://github.com/sakti1977/Harness-Engineering/blob/a800a594297451eab10e6ff0c9cde94a3e31aca0/docs/authority.md))

### Phase 0: repair trust and correctness — approximately 2–4 maintainer days

Audit the current public repository, preserve a reproducible baseline and resolve false-green behavior before promoting adoption. The detailed repository findings and exact source links appear in [the target repository audit](../research_notes/Harness%20knowledge%20base%20expansion/target_repository_plan.md). Add fail-closed ledger validation, meaningful negative tests, CI that runs those tests, an accurate README, and a license selected by the owner. Ensure every referenced example file and proof command exists or is explicitly labeled illustrative. Separate validation of evidence fields from verification that evidence was produced by the claimed run. Acceptance means malformed and unknown states are rejected, documented commands work in a clean checkout, and CI catches the intentionally broken variants. In parallel, retain the legacy source index and add source metadata and scenario labels to the most-used vault notes.

### Phase 1: release a usable starter — approximately 5–8 maintainer days

This phase depends on the Phase 0 checks. Deliver one complete local reference project, one no-key red/green walkthrough, a compact template pack, a read-only diagnostic command and two carefully chosen adapters based on actual maintainer test capacity. Codex and Copilot are reasonable initial candidates given the research coverage and existing Copilot note; verify their current contracts before implementation. Include an environment manifest, scoped task contract, authority policy, feature ledger, verification matrix, journal/checkpoint example and evidence receipt. Acceptance means at least three unfamiliar users can follow the clean-checkout instructions and identify the deliberately injected failure without maintainer intervention. Record their time and errors rather than promising a setup duration before measuring it.

### Phase 2: publish the evidence and learning spine — approximately 1–2 maintainer weeks

This phase depends on a stable starter and schemas. Add the highest-priority notes on harness versus evaluation harness, reproducible environments, tool usability, grader reliability, retries, idempotency, memory scope and source maintenance. Add a small task bank, repeated-trial runner, outcome graders and an experiment log. Publish at least one baseline-versus-change comparison with raw results, pinned versions and cost/latency alongside success. Keep optimization tasks separate from held-out tasks, and report regressions even when the overall score rises. An initial pack of roughly 8–12 carefully specified tasks is more useful than a large unreviewed task collection; the count is a planning choice, not a scientific minimum. ([Anthropic evaluations](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents); [LangChain harness improvement workflow](https://www.langchain.com/blog/better-harness-a-recipe-for-harness-hill-climbing-with-evals))

### Phase 3: demonstrate portability and operational behavior — approximately 2–4 maintainer weeks

This phase depends on stable evaluation and contribution contracts. Add a second genuinely different reference project, then additional adapters supported by tested capability matrices. Extend labs to process-enforced forbidden writes, connector authorization fixtures, cancellation, crash recovery, trace lineage and model-upgrade ablations. Compare a simple baseline against each extra mechanism; show both benefit and overhead. Do not claim production readiness from a local demonstration. OpenHands separates execution, workspaces and remote servers from application concerns; Anthropic's chat demo explicitly identifies authentication, storage and isolation as additional production work. Use those distinctions to define a deployment checklist with testable boundaries. ([OpenHands SDK](https://github.com/OpenHands/software-agent-sdk); [Anthropic chat demo](https://github.com/anthropics/claude-agent-sdk-demos/blob/main/simple-chatapp/README.md))

### Keep the first three pull requests independently reviewable

**PR 1 — truthful validation and regression tests:** change the readiness label, handle parse errors, validate object shape, required field types, allowed states and empty values, and add CI plus seeded invalid fixtures. Its acceptance gate is an automated clean-checkout run that accepts valid artifacts and rejects every documented malformed case with actionable output. This is the prerequisite for the other two PRs.

**PR 2 — complete model-free adoption example:** supply the missing booking application and tests, a red/green failure demonstration, filled templates, trusted verification commands and clear setup/reset instructions. Update the README to match exactly what exists. Its acceptance gate is independent reproduction of both the failure and correction with a result tied to the tested revision. Keep optional live-model execution outside the default path.

**PR 3 — source-backed learning and contribution release:** connect the vault and handbook through one canonical content source, add source and case templates, preserve legacy attribution, publish initial learning routes and add contribution/support guidance. Include license terms only after the owner selects them. Its acceptance gate is resolved navigation, inspectable provenance for new factual claims and an unfamiliar reader reaching the matching runnable example from a documented symptom. Read-only diagnostics can follow these PRs; do not overload the first correctness repair with a new product interface.

### Phase 4: maintain a community resource — ongoing after the starter is reliable

Assign ownership by topic and adapter, publish a support matrix and archive stale integrations visibly. Add issue templates for reproduction reports, source corrections and proposed recipes; require new recipes to bring a fixture, provenance and limitations. Review broken links and runnable examples in CI, review source freshness on a manageable schedule, and trigger deeper reviews on model, dependency or specification changes. Monthly source triage and quarterly experiment review are suggested starting cadences, to adjust to maintainer capacity. Separate syntactic link checks from human verification that the source still supports the claim.

## Earn adoption through outcomes people can verify

The launch should demonstrate one concrete transformation: a project previously accepted a false-green completion; the starter now catches it, explains it and records proof of the fix. Put this demonstration near the top of the README with a short walkthrough, a screenshot or compact recording, and links to the exact fixture and results. Offer a clear beginner path, a project-maintainer path and a contributor path. A public documentation site can follow once the content structure is stable; generate it from the maintained source rather than creating another independently edited copy.

After the first outside users succeed, publish technical walkthroughs tailored to the communities whose tools are actually supported. Link upstream fairly, contribute legitimate fixes upstream when found, and invite reproduction and criticism. Avoid mass-posting, unsolicited messaging, star exchanges or unsupported “best in the world” claims. A comparison should explain scope, versions and tradeoffs rather than rank unlike tools by a headline score. Maintainers should ask satisfied users to share the resource only after it has solved a concrete problem.

Measure the adoption funnel: documentation visitors, starter attempts where voluntarily observable, successful first runs reported by users, repeated use, issues resolved, external reproduction reports and contributions accepted. Track GitHub stars, forks and owner-visible clone traffic as distribution signals, with collection dates and available reporting-window limits. Public clone totals and active-use totals cannot be inferred from star counts. Set initial operational targets such as three successful outside walkthroughs before launch and five independently reproduced cases before a major claim; these are proposed goals, not achieved outcomes. Evaluate whether readers can correctly choose and test a control, not just whether the page attracts attention.

## Conclusion

The opportunity is to connect ideas that usually live apart: a readable knowledge graph, a small implementation kit, and reproducible evidence about when a change helps. That combination lets a reader move from an incident to a mechanism, a working fixture, a project adaptation and a measured decision. A source collection alone cannot provide that experience, and a template collection without proof cannot establish reliability.

This research delivers a plan and navigable evidence, not completed repository fixes, runnable benchmarks or guaranteed adoption. The next concrete milestone is a verified starter release that an unfamiliar developer can use successfully. Let its failures guide the next lessons and its measured limits constrain the claims; that is how the resource can become worth returning to, contributing to and recommending.
